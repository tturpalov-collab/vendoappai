# vendoappai — аналитика платежей

## Что это за задача

Аналитика по платежам из production-базы (PostgreSQL на AWS RDS).
Пользователь хочет, чтобы **данные собирал и анализировал ассистент**, а не
запускал скрипты руками. Не предлагайте ему «вот скрипт, запустите» — поднимайте
туннель, ходите в базу и делайте выводы сами, показывая пользователю результат.

## Доступ к базе

База в приватной сети, доступ только через SSH-туннель к bastion-хосту:

```
ssh -L 54322:vendo-app.cvwxd0jliglu.eu-central-1.rds.amazonaws.com:5432 ec2-user@18.196.28.193 -i <ключ>
```

Пользователь БД — `vendo_ai_reader`, **read-only**. Пароль и путь к ключу лежат
в `analytics/.env` (не в git). Если файла нет — попросите пользователя создать
его из `analytics/.env.example`.

> Важно: это **не работает** из Claude Code на вебе — там исходящий порт 22
> заблокирован сетевой политикой окружения, и `ssh` не установлен. Задача
> рассчитана на локальный запуск (CLI / десктоп-приложение).

## Инструменты (запускает ассистент, не пользователь)

Все скрипты самодостаточные: сами поднимают SSH-туннель, сами ставят `psycopg`,
работают из любой папки. Пароль берут из `PGPASSWORD`, `analytics/.env` или спрашивают.

| Скрипт | Что делает |
|---|---|
| `vendo_payments.py` | Разведка: находит нужную базу и платёжные таблицы, профилирует их |
| `vendo_analytics.py` | 18 разрезов: выручка, отказы, организации, города, автоматы, товары, карты, чек, часы, дни |
| `vendo_drilldown.py` | 17 разрезов детализации: потери по автоматам, зоны по техотказам, август и `CE` по организациям, темп запуска, не запущенные машины |
| `vendo_export.py` | Выгрузка в CSV: сырые платежи поквартально (под лимит 30 МБ) + витрины + телеметрия модулей |

Старые обёртки для `psql` (`tunnel.sh`, `db.sh`, `sql/*.sql`) оставлены на случай,
если на машине есть `psql`, но основной путь — питоновские скрипты.

## Если нет psql

`psql` на машине может отсутствовать (Homebrew недоступен из-за сетевых
ограничений — `raw.githubusercontent.com` режется). Не заставляйте пользователя
что-то ставить руками: разберитесь сами.

Порядок предпочтений:

1. `psql` — проверить `command -v psql`, а также
   `/Applications/Postgres.app/Contents/Versions/latest/bin/psql`.
2. Python + `psycopg`: `python3 -m pip install --user "psycopg[binary]"`
   (pypi.org обычно доступен). Туннель поднимается тем же `analytics/tunnel.sh`,
   а запросы идут через `psycopg.connect(host="127.0.0.1", port=54322, ...)`,
   параметры берутся из `analytics/.env`.

Во втором случае положите тонкую обёртку в `analytics/query.py`, чтобы
дальнейшие запросы шли одной командой, и обновите этот раздел.

## Порядок работы

1. Схема базы пока не разобрана — начните с `00_discover.sql` и разберитесь,
   где лежат платежи, какие статусы, валюты и связи с пользователями/заказами.
2. Запишите разобранную схему сюда, в раздел «Схема», чтобы следующие сессии
   не повторяли разведку.
3. Дальше — витрины под запросы пользователя: выручка по периодам, средний чек,
   конверсия, возвраты, разрезы по методам оплаты и когортам.
4. Готовые запросы складывайте в `analytics/sql/` с говорящими именами.

## Бизнес-контекст

Компания — **дистрибьютор** вендинговых автоматов в ОАЭ. В `vendotek_unit` лежит
**весь поставленный парк**, включая ещё не введённое в эксплуатацию железо.

- 1008 автоматов в справочнике, 290 когда-либо продавали, 267 торгуют за 30 дней.
- **718 автоматов без продаж — это не поломка, а запас**, но запас неоднородный:
  - **298 выходили на связь за последние 30 дней** (85 — за неделю) и не продали
    ничего. Из них у 206 заполнен адрес. По медиане это до ~451 тыс. AED/мес,
    **но это верхняя граница**: в выборке машин на связи с адресом 30 из 38 стоят
    по одному адресу `104 DAMASCUS STREET AL QUSAIS` — это депо оператора,
    а не 30 точек. Сколько реально развёрнуто, считает запрос 24.
  - **306 замолчали разом в декабре 2025** и больше не появлялись — похоже на
    партию, завезённую и убранную на склад.
  - остальные ~114 разбросаны по месяцам или без внятной отметки.
- Адрес заполнен у 266 из 718, на связи в августе — 274. Похоже, адрес появляется
  ровно тогда, когда машину ставят на точку.

### Авария марта 2026

Скачок отказов до 27 % в марте—апреле 2026 — следствие **аварии дата-центра AWS
в ОАЭ**: переезд в другой ЦОД прошёл тяжело, сетевые задачи разгребали ещё 2–3
месяца. Хвост виден в данных: 12,5 % отказов в мае, 12,3 % в июне, 10,4 % в июле,
6,6 % в августе.

Это объясняет структуру отказов: `CE` и пустой код ответа — сетевой уровень, а не
решение банка. Не интерпретировать их как отказы эмитента.

### Пустой код ответа — это НЕ всегда отказ

Терминалы `soco-br-of-majid-al-futtaim` стоят в **парке развлечений**, где у
посетителей свои карты MiFare с балансом для игровых аппаратов. Люди прикладывают
их к нашему POS по ошибке; POS видит неплатёжную карту и отклоняет её с пустым
`response_code`.

**Это не отказ в оплате и не потерянная выручка — покупки не было вовсе.**

- В августе 2 509 таких событий — 96 % всех пустых кодов по компании.
- За всю историю ориентировочно 26 700 из 27 792 пустых кодов.
- Отсюда «хронические 63,9 % отказов у soco в феврале, до аварии» — это не авария
  и не поломка, а ровный фон промахов по ридеру.

**Подпись промаха чистая и не привязана к организации:**

```sql
pos_entry_mode = 'CONTACTLESS' and coalesce(aid,'') = '' and coalesce(pan,'') = ''
```

Так помечено 26 065 событий — 98,7 % всех промахов. У настоящих оплат
`pos_entry_mode` всегда `EMV CONTACTLESS` или `QR CODE READ`; простой
`CONTACTLESS` с пустыми AID и PAN встречается только при чужой карте.
Фильтровать этим правилом, а не по имени организации — сработает на любой площадке.

**Любую метрику отказов считать с исключением этих событий**, иначе approve rate
компании занижен примерно на 3 п.п. (87,2 % вместо 90 с лишним).

Пересчёт с этой поправкой:

- базовая линия отказов — **3,4 %** (декабрь—февраль без soco), а не 7 %;
- март 19,37 %, апрель 21,73 %, май 5,67 %, июнь 8,20 %, июль 5,95 %;
- **август без soco — 3,49 % против 3,33 % в феврале: сеть восстановлена полностью**;
- потери за март—август — **330 684 AED**, это 23 919 несостоявшихся покупок
  и 5,3 % выручки за период (в августе недобор уже 883 AED, то есть его нет).

**Незакрытый хвост:** в июне 1 142 пустых кода пришли **не** из парка развлечений
(в мае — 1, в июле — 121, в августе — 105). Отдельное событие, поднявшее июнь
до 8,20 %. Причина не установлена.

### Что уже выяснено по отказам

- **Сеть починена.** `CE` упал с 847 за неделю (пик 15 июня) до 37 (неделя 17 августа),
  −96 %. За август 574 против 10 932 в апреле. Последствия аварии AWS закрыты.
- **Пустой код ответа вниз не идёт** — но это и не сбой, см. раздел выше про MiFare.
- **Автомат `221400017033`** — 790 попыток, 790 технических отказов, ноль продаж
  за всю историю. Неисправный терминал, а не связь. В августе дал 174 `CE` — 30 %
  всех обрывов по компании.
- **20 игровых автоматов** (`PINBALL`, `AIR HOCKEY`, `NBA HOOPS`, `ON TARGET`,
  `KICK AND PUNCH`) с чеком ровно 12,00 AED и долей техотказов 46–80 %.
  Суммарно 329 425 AED. Одинаковый чек и одинаковая болезнь — общая причина.
- **Зоны по доле техотказов:** 23 автомата свыше 30 % дают 358 492 AED потерь;
  63 автомата в 5–15 % дают ещё 432 081 AED; 124 машины ниже 5 % — 60 тыс., их не трогать.

### Темп запуска и потенциал

25,7 машины в месяц за последние полгода (август — рекорд, 37). На оставшиеся 718
при таком темпе нужно 28 месяцев. Типичная машина приносит **≈1 500 AED в месяц
(медиана июля)**, среднее 4 542 завышено перекосом — планировать по медиане:
718 машин дадут порядка 1,1 млн AED в месяц, а не 3,3 млн.

### Ещё одна ловушка

`vendotek_unit.last_seen_at` хранит **секунды** эпохи, а не миллисекунды.
Делить на 1000 нельзя — получится январь 1970-го. В скриптах стоит проверка
`case when last_seen_at > 100000000000 then /1000 else as is end`.
Для `vendotek_module.status_changed_at` формат не проверен.

### Классификация отказов

Технический отказ (терминал не получил внятного ответа от хоста):
`response_code` пустой, `CE`, `TO`, `907`, `909`, `911`.
Банковский отказ: всё остальное, прежде всего `116` (недостаточно средств).
За весь период: 54 830 технических против 13 058 банковских — 81 % против 19 %.

## Схема

База `app` на сервере (не `postgres` — та пустая), PostgreSQL 18.3, схема `public`,
16 таблиц с префиксом `vendotek_`. Данные — зеркало внешней системы Vendotek:
почти везде есть `synced_at`, у части таблиц `dirty` / `external`.

**Предметная область: вендинговые автоматы в ОАЭ.** Валюта во всех продажах — `AED`,
организация `vendotek-uae`. Цены в `vendotek_planogram_product.price` — `bigint`,
предположительно в филсах (1 AED = 100 fils), проверять перед использованием.

### Связи

**Внешних ключей в базе нет** — связи только логические, по `uuid`:

```
vendotek_payment.vend_id           -> vendotek_vend.id
vendotek_payment_cash.payment_id   -> vendotek_payment.id
vendotek_payment_cashless.payment_id -> vendotek_payment.id
vendotek_vend.unit_id              -> vendotek_unit.id
vendotek_unit.owned_by_org_id      -> vendotek_org.id
vendotek_vend_planogram_product_link.vend_id -> vendotek_vend.id
```

Проверка сходимости: 68 180 (cash) + 467 044 (cashless) = 535 224 = ровно число
платежей. То есть у каждого платежа ровно одна строка детализации.

### Ловушки — читать перед любым запросом

1. **`synced_at` — это НЕ дата операции**, а момент выгрузки из внешней системы
   (вся выгрузка приходится на 19–25 августа 2026). Агрегировать по нему нельзя:
   получится вся выручка в одном месяце. Реальное время операции —
   `vendotek_payment.pos_localtime_at` (`timestamp without time zone`, локальное
   время терминала; смещение в `pos_localtime_offset_s`). Диапазон данных:
   **2025-05-06 … 2026-08-25**.
2. **Сумма платежа = `cash_amount + cashless_amount`.** По отдельности каждое поле
   заполнено только для своего типа оплаты, у остальных ноль — средний чек по одной
   колонке занижен в разы.
3. **Статусов-enum нет.** Успех платежа — булев `approved`; у безнала дополнительно
   `response_code` (`000` = успех). Отмена продажи — `vendotek_vend.cancelled`.
4. В ранних данных (май–сентябрь 2025) много транзакций на 0.01–0.04 AED — похоже на
   тестовые прогоны. Для бизнес-метрик их стоит отфильтровывать.

## Правила

- Учётка read-only: только `SELECT`. Ничего не писать и не менять в базе.
- Секреты (`.env`, ключи) и выгрузки из `analytics/out/` — в `.gitignore`,
  в репозиторий не коммитить.
- На больших таблицах ставить `LIMIT` при разведке; для агрегатов сначала
  проверять объём через оценку строк.
